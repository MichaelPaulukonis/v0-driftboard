# 10. MCP Read Access (local, read-only)

## Problem Statement

Driftboard is only reachable through the web UI. I want my Claude-based task workflows to read boards, lists, cards, and comments directly, so the app becomes part of daily tooling (more use → more bugs found → more development). It doubles as a job-hunt showpiece: a real app with a real MCP integration.

Remote access is not needed now. A later HTTP/remote phase (personal access tokens, server-side authz) is out of scope here but the design must not block it.

## Requirements

- Local stdio MCP server, runnable from Claude Code on macOS.
- Read-only: no tool may write to Firestore.
- Authenticates as the real user (email/password); Firestore security rules enforce access exactly as they do for the browser. No service account / Admin SDK.
- Tools (initial set):
  - `list_boards` - active boards the user owns or is a member of, with role.
  - `get_board` - board + active lists (ordered) + active cards per list.
  - `get_card` - single card with its comments.
  - `search_cards` - case-insensitive text match on title/description across the user's boards (optional `boardId`).
- Works against the Firebase emulator for tests and demos.
- A Claude Code skill that uses the tools for task workflows (e.g. "what's on my Driftboard today").
- Portfolio-quality README for the integration, with a short demo GIF.

## Technical Approach

- New `mcp/` directory in this repo, using `@modelcontextprotocol/sdk` (stdio transport), run via `tsx`.
- Reuse `lib/firebase-service.ts` and `lib/types.ts` directly - the service layer is plain Firebase client SDK configured from env vars, so it runs outside Next.js. No duplicated query logic.
- Tools depend on a small `DriftboardReader` interface, not on `firebase-service` directly. Phase A implementation wraps `firebase-service`; a future HTTP implementation can replace it without changing tool names, schemas, or outputs.
- Auth: `signInWithEmailAndPassword` at startup. Credentials from env (`DRIFTBOARD_EMAIL`, `DRIFTBOARD_PASSWORD`), populated from the macOS Keychain in the MCP launch command (`security find-generic-password -w ...`). Firebase config from the existing `NEXT_PUBLIC_FIREBASE_*` vars.
- Emulator: honor existing `NEXT_PUBLIC_USE_EMULATOR=true` handling in `lib/firebase.ts`.
- Read-only is enforced by the tool surface (only read methods exposed through `DriftboardReader`). Rules would still permit writes as this user; acceptable for personal local use.
- Output: compact JSON (ids, titles, status, dates as ISO strings); omit history and internal fields.

## Implementation Steps

1. Spike: import `firebase-service` from a `tsx` script, sign in, call `boardService.getUserBoards()`. Confirm no Next.js-only imports break it.
2. Define `DriftboardReader` interface + Firebase-backed implementation.
3. MCP server skeleton with `list_boards`; register in Claude Code (`claude mcp add`), verify end to end.
4. Add `get_board`, `get_card`, `search_cards`.
5. Tests against the emulator (seeded user, boards with owner/viewer membership, deleted items excluded).
6. Write the skill (task-workflow usage of the tools).
7. README section + demo GIF.

## Testing Strategy

- Vitest tests for `DriftboardReader` and tool handlers against the Firestore/Auth emulator (`firebase emulators:exec`, like `test:rules`).
- Cases: owned board, shared board as viewer, board the user has no access to (must fail/omit), soft-deleted lists/cards excluded, card with comments.
- Manual: register in Claude Code, run each tool against prod data.

## Risks & Mitigation

- **Service layer has hidden browser/Next deps** - step 1 spike surfaces this first; fix by isolating imports rather than forking logic.
- **`getBoardCards` uses Firestore `in` with all list ids** - `in` caps at 30 values; boards with >30 lists would fail. Tracked as `v0-driftboard-kle` (chunk, as `getCardsByStatus` already does); broader limits audit in `v0-driftboard-a3v`.
- **N+1 in `getCardComments` (`v0-driftboard-m7w`)** - makes `get_card` slow on busy cards; fix if it bites.
- **Password in env** - kept in Keychain, injected at launch only; never committed.
- **Interface drift for future HTTP phase** - tools only talk to `DriftboardReader`.

## Dependencies

- `@modelcontextprotocol/sdk`, `tsx`, `zod` (tool schemas) - dev/runtime deps for `mcp/`.
- Firebase emulator setup (already present: `pnpm emulators`).
- Optional: `v0-driftboard-m7w` (comments N+1).
- Future phase B (remote MCP/HTTP API with tokens) depends on `v0-driftboard-ly3` (type-check + lint in build).
